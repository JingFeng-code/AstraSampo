# AstraTube 2.0 開發規劃（草稿，待確認）

> 狀態：**規劃草稿**。這份文件描述的功能除非特別註明「已有」，否則都**尚未實作**。
> 撰寫日期：2026-11-17。依據：`main`（f50f13c）與 `feat/ollama-cloud-and-ux`（PR #59）的程式碼現況。

## 1. 目標與原則

**2.0 的目標**：從「功能越加越多」轉成「內容可以信任、操作順手」。使用者要能快速吸收影片內容，而且知道哪些資訊可以信、哪些要回原片確認。

**不做的事**
- 不重寫專案，維持 React + FastAPI + Tauri。
- 不同時啟動多個階段；每個階段有明確的結束條件，達到才進下一個。
- 不為了提高準確度讓每支影片多呼叫好幾次模型；能用程式檢查的就不用模型。

**每個 PR 都要遵守**
- 一件事一個分支、一個 PR，附 mock 測試；不直接提交 `main`、不自動合併。
- 合併前讀 PR 上的審查留言。
- CI 通過不等於實機通過；回報一律寫「自動化測試通過，實機未驗收」直到真的驗收過。
- 選 Ollama 時不得默默改用雲端；影片文字、API 回應一律視為不可信輸入。

## 2. 現況盤點（規劃的依據）

| 面向 | 現況 | 影響 |
|---|---|---|
| 摘要提示詞 | 要求「寫學到什麼，不是講者說了什麼」，並禁止出現「講者提到」 | 模型會把「誰說的」拿掉，個人經驗容易被寫成普遍事實 |
| 引用 | `transcript_highlight` 要求照抄原文，但程式沒有檢查它是否在原文裡 | 引用可能是模型改寫或編的，使用者看不出來 |
| 時間戳 | 只檢查卡片有沒有涵蓋到影片尾端 | 卡片時間可能對不上內容 |
| 語音辨識 | SenseVoice 自動語言，不支援熱詞 | 專有名詞錯誤只能在辨識後校正 |
| 問答 | 整份逐字稿最多取前 60,000 字元；回答裡的時間點不能點 | 長影片後段問不到；答案無法一鍵查核 |
| 閱讀 | 播放器和字幕要等分析完才出現；字幕有搜尋與點擊跳轉 | 不能「先看再決定要不要分析」 |
| 收藏 | 只記住最後一支影片 | 沒有影片庫 |
| 測試 | 都是 mock，檢查流程不檢查內容品質 | 改提示詞或換模型後，無法知道品質變好還是變差 |
| 文件 | `ROADMAP.md`、`BETA_READINESS.zh-TW.md`（2026-10-29）與實際進度不同步；Issue #23 多項已實作未打勾 | Agent 可能依過期資訊重複開發 |

## 階段 1：影片分析品質基準

### 1A　程式可檢查的部分（進 CI）

新增 `backend/app/services/grounding.py`，對每張卡片做三項不呼叫模型的檢查：

1. **引用是否存在**：`transcript_highlight` 的每一句能不能在原文找到（容許標點、空白、簡繁差異）。
2. **時間戳是否合理**：`timestamp_seconds` 是否落在該段素材範圍內，且引用所在行的時間與它相差不超過設定值。
3. **數字是否有出處**：摘要裡的數字（百分比、金額、年份、數量）是否出現在該段素材。

第一步**只記錄不顯示**（寫進回應的 `grounding` 欄位與後端紀錄），避免還沒校準就誤報。

測試：`backend/tests/test_summary_grounding.py`，用手寫的小型素材與卡片，涵蓋找得到／找不到／簡繁不同／時間超出範圍。

### 1B　需要真的跑模型的部分（不進 CI）

- 測試資料：`backend/tests/fixtures/quality/<影片代號>/`
  - `claims.json`：人工挑的 15–20 個重點，每個有原文短引用、時間、正確說法、容易錯的地方。
  - `glossary.json`：這支影片的專有名詞正確寫法。
  - **不放整份逐字稿**（那是別人影片的內容）；完整逐字稿留在本機，路徑加進 `.gitignore`。
- 評測腳本：`scripts/eval_quality.py`，輸入一份逐字稿與模型，輸出卡片、1A 的檢查結果、耗時，並產生待人工評分的表格。
- 四種流程（同一版本、同一模型、同一參數）：

| 代號 | 素材 | 要回答的問題 | 誰跑 |
|---|---|---|---|
| A | YouTube 原生字幕 | 不經語音辨識時摘要品質如何 | 可在開發機用本機 Ollama 跑 |
| B | 陪看：只有聲音 | 本機語音辨識造成多少錯 | 只能在桌面版實機跑 |
| C | 陪看：聲音＋畫面 | 畫面筆記有沒有補到有用資訊 | 只能在桌面版實機跑 |
| D | 人工校正的逐字稿 | 排除辨識錯誤後摘要還會不會誤解 | 可在開發機跑 |

- 報告：`docs/QUALITY_BASELINE.md`（方法與固定條件）、`docs/QUALITY_EVALUATION.md`（每次結果）。

### 1C　評分方式

每個重點人工標「正確／部分正確／錯誤／遺漏」，錯誤再分類：

| 類別 | 例子 |
|---|---|
| 辨識錯字 | `pull requests` 被辨識成 `plocrs` |
| 歸屬錯誤 | 某人的個人經驗被寫成普遍情況 |
| 數字錯誤 | 數字不對，或數字代表的東西不對 |
| 無中生有 | 原文沒有的內容 |
| 時間錯位 | 卡片時間對不到內容 |

第一支影片只當**檢查清單**用，不算百分比。補到 3–5 支不同類型（英文演講、有簡報的中文教學、Bilibili）後才訂門檻。建議門檻（開發目標，不是現況）：

- 重大事實錯誤且未標示：0
- 引用能在原文找到：100%
- 數字與人物歸屬：100% 經人工核對
- 時間戳在對應片段前後 10 秒內：≥ 95%
- 專有名詞正確：≥ 95%

### 1D　依結果決定下一個 PR

| 如果發現 | 下一步 |
|---|---|
| D 仍有歸屬錯誤（依提示詞現況，預期會發生） | 改提示詞：保留「誰說的、數字代表什麼、適用範圍」；卡片顯示「未在原文找到」標記 |
| B 的錯主要是專有名詞 | 辨識後校正：使用者詞彙表＋從標題與說明取詞；`test_transcript_correction.py` |
| C 沒有比 B 好 | 暫緩畫面模型優化，階段 4 的陪看項目延後 |
| 品質已足夠 | 直接進階段 2 |

**結束條件**：1A 進 CI；A／D 至少各跑過一次並有人工評分；做完一輪改善並用同一份資料量到前後差異。

## 8. 風險

| 風險 | 對策 |
|---|---|
| 只用一支影片調提示詞，換影片就變差 | 至少 3–5 支不同類型；改提示詞一定跑全部資料 |
| 為了忠實度讓卡片變得囉嗦 | 評分同時記「好不好讀」；歸屬只在數字與主張上保留 |
| 程式檢查誤報（簡繁、標點、翻譯後的引用） | 先只記錄不顯示，校準後才顯示 |
| 本機模型結果每次不同 | 固定溫度與種子；每個流程跑 2–3 次看變動範圍 |
| 階段 2 改首頁流程影響現有使用習慣 | 先做原型確認再實作 |

## 9. 需要你確認的決定

1. **產品定位**：現在提示詞寫的是「用卡片取代看影片」。建議改成「幫你讀影片，重點都能回原片查核」。這會決定提示詞要不要保留「誰說的」。
2. **Bilibili SESSDATA 與自動下載音訊**：先前決定是不做登入、不下載。PR #59 兩個都做了。要保留的話，建議改成使用者主動按才執行，並在文件寫明條款風險。
3. **評測影片**：第一支用 `O_zcc6Xl12g`；另外 2–4 支由你指定。人工標註由你做，每支約 30–60 分鐘。
4. **整體總結**：每次分析多呼叫一次模型。要預設開啟，還是做成開關？
5. **先看後析**：階段 2 會改變首頁流程，是否同意先做原型？
6. **分工**：由我規劃並實作，還是我規劃、Codex 實作、我審查？
